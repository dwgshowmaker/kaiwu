# 代码规范

## 文档目标

本文档记录峡谷追猎项目在 `agent_diy` 方向上的开发规范。后续每次修改代码、训练流程、奖励设计或特征结构时，都要同步检查并更新本文档，确保实现、文档和实验记录保持一致。

---

## 一、开发边界

### 1. 默认开发目录

新策略、新特征、新奖励、新模型默认都放在 `agent_diy` 下实现。

`agent_ppo` 作为稳定参考基线，除非明确说明，不在迭代中修改。

### 2. 代码职责

| 路径 | 职责 |
| :-- | :-- |
| `agent_diy/agent.py` | Agent 推理、动作处理、模型保存加载 |
| `agent_diy/algorithm/algorithm.py` | PPO 损失、优化器更新、训练指标上报 |
| `agent_diy/conf/conf.py` | 特征维度、动作维度、PPO 超参数 |
| `agent_diy/feature/definition.py` | 数据结构、样本字段、GAE 计算 |
| `agent_diy/feature/preprocessor.py` | 特征处理、奖励塑形、局内状态缓存 |
| `agent_diy/model/model.py` | Actor-Critic 网络结构 |
| `agent_diy/workflow/train_workflow.py` | 环境交互、采样、终局奖励、监控上报 |
| `agent_diy/conf/monitor_builder.py` | 自定义监控面板 |

## 二、代码风格

### 1. 命名规范

- Python 文件、变量和函数使用 `snake_case`
- 类名使用 `PascalCase`
- 常量使用 `UPPER_SNAKE_CASE`
- 特征分组命名尽量和 `Config.FEATURES` 对齐，例如 `hero_feat`、`monster_feats`、`map_feat`

### 2. 注释规范

- 只在非显然逻辑前添加简短注释
- 奖励项、特征维度、动作维度必须有注释说明
- 不写“给变量赋值”这类低信息量注释

### 3. 导入规范

导入顺序建议为：

1. 标准库
2. 第三方库
3. 项目内部模块

示例：

```python
import os
import time

import numpy as np
import torch

from agent_diy.conf.conf import Config
```

## 三、特征规范

### 1. 特征维度必须单点维护

特征结构发生变化时，必须同步修改：

- `agent_diy/conf/conf.py` 中的 `FEATURES`
- `agent_diy/conf/conf.py` 中由 `FEATURES` 推导出的 `DIM_OF_OBSERVATION`
- `agent_diy/feature/definition.py` 中 `SampleData.obs`
- `agent_diy/feature/preprocessor.py` 中实际拼接出的特征长度

### 2. 特征拼接要求

特征拼接顺序必须稳定，不能在训练中动态变化。

推荐顺序：

1. hero 特征
2. monster 特征
3. treasure 特征
4. buff 特征
5. map 特征
6. legal action 特征
7. progress 特征

Phase 2 当前实际特征布局为 **234 维**：

| 分组 | 维度 | 说明 |
| :-- | --: | :-- |
| hero | 8 | 坐标、闪现冷却、buff、步数进度 |
| monsters | 16 | 2 只怪物，每只 8 维 |
| treasures | 10 | 最近 2 个宝箱，每个 5 维 |
| buffs | 10 | 最近 2 个 buff，每个 5 维 |
| local map | 170 | 局部地图特征为 coarse 7x7 + center 11x11 |
| legal action | 16 | 8 个移动 + 8 个闪现动作合法性 |
| progress | 4 | 第二怪物、怪物加速、宝箱/buff 收集比例 |

### 3. 特征值范围

- 连续数值尽量归一化到 `[0, 1]` 或 `[-1, 1]`
- 布尔特征使用 `0.0 / 1.0`
- 缺失实体使用全零向量
- 不把原始大坐标直接塞进模型

### 4. 动作概率数值稳定性

- `agent_diy/agent.py` 中所有策略概率在采样前必须做一次显式归一化
- 归一化时要处理 `NaN`、`Inf`、负数和总和接近 `0` 的情况
- 采样逻辑不要依赖对浮点和极度敏感的接口行为，优先使用累计概率采样
- 安全先验混合后的概率也必须再次归一化后才能写回 `ActData.prob`

### 5. 维度检查

`preprocessor.py` 中建议保留特征长度断言：

```python
assert len(feature) == Config.DIM_OF_OBSERVATION
```

如果后续训练环境对断言敏感，可以改成日志报错，但开发阶段优先保留断言。

## 四、奖励规范

### 1. 奖励设计原则

奖励要贴近比赛目标：

- 活得更久
- 拿更多宝箱
- 合理吃 buff
- 避免撞墙和原地抖动
- 后续阶段再鼓励合理闪现

Phase 1 当前奖励项：

| 奖励项 | 实现 |
| :-- | :-- |
| 生存奖励 | 每步 `+0.02` |
| 怪物距离塑形 | 最近怪物距离增加给正奖励，危险状态下权重更高 |
| 宝箱奖励 | 宝箱计数增量 `+1.2` |
| buff 奖励 | buff 计数增量 `+0.5`，危险时 `+0.7` |
| 卡住惩罚 | 连续原地不动从第 2 步开始惩罚 |
| 撞墙动作惩罚 | 最近导致原地不动的动作进入短期冷却，危险时额外惩罚 |
| 近身危险惩罚 | 怪物距离小于等于 5 格时惩罚，2 格内惩罚更强 |
| good flash 奖励 | 闪现后明显拉开怪物距离，或顺路拿到宝箱/buff 时奖励 |
| bad flash 惩罚 | 闪现后没有明显脱险、也没有获得收益时轻惩罚 |
| flash follow-up 惩罚 | 闪现后 3 步内仍 near_death 或 blocked 时追加惩罚 |
| 阶段生存奖励 | 存活达到 `200/400/600/800` 步时给一次性 milestone 奖励 |

### 2. 事件奖励优先用差分

以下奖励应基于计数差分：

- 宝箱奖励：`treasure_collected_count` 或 `treasures_collected` 的增量
- buff 奖励：`collected_buff` 的增量
- 闪现奖励：`flash_count` 的增量

不要只凭位置猜测事件是否发生。

### 3. 奖励状态缓存

`Preprocessor.reset()` 必须重置所有跨步缓存，例如：

- 上一步英雄位置
- 上一步最近怪物距离
- 上一步宝箱数
- 上一步 buff 数
- 上一步闪现次数
- 连续卡住计数

## 五、动作规范

### 1. Phase 2 扩展到 16 动作

当前动作空间为：

- `0-7`：八方向移动
- `8-15`：八方向闪现

### 2. Phase 1 安全动作先验

训练日志显示早期策略大量在 30 步内失败，主要问题不是训练链路报错，而是随机探索阶段离怪物过近、样本质量过差。

因此 Phase 1 允许在 `agent_diy/agent.py` 中加入轻量安全先验：

- 只在 `danger_level >= 0.25` 时生效
- `safe_action` 可在 16 动作内选择，但闪现动作要经过更严格的保守评分
- `safe_action` 评分必须考虑远离最近怪物、目标格通行性、后续 3 格通路长度、局部开阔度和撞墙动作冷却
- 如果 `safe_action` 是闪现，还必须额外考虑落点边缘风险、落点局部开阔度，以及相对 `best_move` 的评分差距
- `Agent.predict()` 中对闪现型安全先验的混合权重必须低于普通移动，但在极高危险下要允许更激进的救命闪现
- 闪现动作在非高危状态下必须有额外惩罚，避免策略把闪现学成默认位移
- 闪现是否优于普通移动，必须经过 move / flash 两路评分比较，不能因为略高一点就默认选闪现
- 只混合动作概率，不改变 PPO 损失公式
- 先验权重最高不超过 `0.6`，避免长期压制策略学习
- `flash_trap_count` 的判定不能过于激进，避免把“短期救命但尚未完全脱险”的闪现全部打成负样本

### 3. 变更动作维度时的模型加载

从 8 动作切到 16 动作后，旧 checkpoint 可能与新模型维度不兼容。

因此必须满足：

- `Config.ACTION_NUM`
- `SampleData.legal_action`
- `SampleData.prob`
- Actor 输出维度
- `Preprocessor` 的合法动作掩码
- 闪现奖励与监控项
- `Agent.load_model()` 在遇到旧维度 checkpoint 时允许跳过加载并记录 warning

## 十、势能化 Shaping 补充规范

在 Phase 1 / Phase 2 内继续迭代时，优先使用可解释的状态势能差分 shaping，
不要无限堆叠彼此冲突的固定系数启发式奖励。

新增 `state_potential` 一类势能状态时，必须满足：

- 主 shaping 优先采用 `gamma * Phi(s') - Phi(s)` 风格
- 势能尽量拆成 `safety/resource/flash` 等可解释子项
- `Preprocessor.reset()` 中同步重置上一步势能缓存
- 闪现随访奖励同时参考距离变化和势能变化，避免只凭单步距离误判

如果本轮已经接入势能诊断，监控建议同时补充：

- `state_potential`
- `safety_potential`
- `resource_potential`
- `flash_potential`

`[GAMEOVER]` 日志建议补充：

- `state_pot`
- `safety_pot`
- `resource_pot`
- `flash_pot`
- `state_pot_avg`
- `safety_pot_avg`
- `resource_pot_avg`
- `flash_pot_avg`

如果日志已经显示 `blocked_count / stuck_count` 长期偏高，但 `flash_trap_count` 没有同步恶化，
优先排查是否存在“回环走老路”问题，并考虑增加 `loop_count` 指标与落点重复惩罚。

## 九、文档同步规范

每次改动后都要检查是否需要同步更新：

- `峡谷追猎/开发指南/PPO迭代开发方案.md`
- `峡谷追猎/开发指南/代码规范.md`
- 相关代码注释

如果代码实现和文档描述不一致，以本轮代码实现为准，并立即更新文档。

### 9.1 加速阶段规范

如果开始针对怪物 `500` 步加速做优化，则以下内容要一起维护：

1. 特征与先验

- 与 `step_no`、`speedup_eta`、`monster_speed` 相关的阶段判断，要集中在 `Preprocessor` 中维护
- `Agent` 侧安全先验如果依赖阶段信息，要通过 `ObsData` 显式透传，不要在 `agent.py` 里重复推断环境规则

2. 日志与监控

- `[GAMEOVER]` 至少要包含 `speedup_prep_steps`、`post_speedup_steps`
- 如果策略显著依赖 buff 或闪现保留状态，还要同步记录 `post_speedup_buffless_steps`、`buff_ready_at_speedup`、`flash_ready_at_speedup`

3. 奖励约束

- 500 步前准备阶段允许提高 buff 奖励、降低宝箱偏好
- 500 步后生存阶段允许进一步压低无 buff 状态下的资源追逐
- 但要优先通过势能与阶段门控实现，不要简单叠很多互相冲突的固定惩罚项

### 9.2 关键备战窗口规范

如果策略开始显式优化 `500` 步前最后一段准备期，则推荐统一遵守：

1. 时间窗口定义集中在 `Preprocessor`

- 最后 `100` 步的保闪窗口
- 最后 `50` 步的 buff 备战窗口
- 不要把这些阈值分散写在 `agent.py`、`workflow.py` 等多个地方

2. 日志与监控同步补齐

- 至少补 `prep_flash_ready_steps`
- 至少补 `prep_buff_active_steps`
- 继续保留 `buff_ready_at_speedup`、`flash_ready_at_speedup`

3. 低价值闪现惩罚要带窗口语义

- 不是所有低危险闪现都一样
- 临近 `500` 步时的低价值闪现，应比普通阶段惩罚更强

4. `loop_count` 必须表示“回环事件”，不能退化成“走久了就涨”

- 只有短窗口内重复落点达到阈值时才记一次
- 如果改了回环判定，必须同步更新文档与日志解释

### 9.3 备战 Buff 先验规范

如果在 `450-500` 步之间引入拿 `buff` 的轻量行为先验，需要遵守：

1. 先验只在低危险阶段启用

- 高危险时仍以逃生先验优先
- 不要让资源先验和逃生先验在同一时刻强行争抢动作

2. 备战先验默认只引导普通移动

- 不要为了拿 buff 在备战阶段默认鼓励闪现
- 闪现应优先保留给 `500` 后高危逃生

3. 先验必须可观测

- 至少记录 `prep_prior_count`
- 至少记录 `prep_action_count`
- 如果修改了窗口阈值或触发条件，也要同步更新文档

### 9.4 多尺度地图表达规范

如果开始直接优化局部地图表达，需要统一遵守：

1. 区分环境原始视野与模型实际输入

- 环境原始 `map_info` 是 `21x21`
- 模型输入可以是下采样或多尺度表达
- 文档里必须同时写清这两个层次，避免把“环境视野”和“模型地图特征”混为一谈

2. 推荐优先做多尺度而不是只改单一分辨率

- coarse 地图负责全局通行趋势
- center 地图负责近身逃生细节
- 不要只保留过粗的压缩地图

3. 改地图特征时必须同步维护

- `Config.FEATURES`
- `Config.DIM_OF_OBSERVATION`
- `Model` 输入维度与隐藏层规模
- `Preprocessor` 的特征长度检查

4. 旧 checkpoint 兼容性

- 如果地图特征维度变化，默认视为与旧 checkpoint 不兼容
- 允许沿用当前 `Agent.load_model()` 的跳过加载保护，但要在最终说明里明确记录
